# ADR-008: Три уровня моделей Ollama по задачам, не одна общая

## 1. Контекст (The Problem)
После [[ADR-007-ollama-primary]] весь трафик шёл на один `ollama-local`. Но задачи Jarvis по своей природе разные:
- `presentation`/`email` — генерация формального русского текста, интерактивно (Виктор ждёт ответ в моменте).
- `report`/`analysis`/`research` — точность данных важнее скорости, менее интерактивно (может крутиться в фоне).
- `task_classification`/`learning_loop` (structured JSON) — должно быть мгновенным, не нужна большая модель.

Одна модель на все случаи — либо слишком медленная для интерактивных задач (если взять крупную ради точности отчётов), либо слишком слабая для отчётов (если взять маленькую ради скорости чата).

Также при первом прогоне `call_ollama` не передавал `num_ctx` — Ollama по умолчанию режет контекст до 2048 токенов независимо от реальной способности модели, что тихо обрезало бы длинные промпты (данные стейкхолдера + структура презентации).

## 2. Предложенное решение (The Decision)
Три именованных tier'а в `models:` вместо одного `ollama-local`, все `api_provider: local`, на базе **Qwen2.5** (сильный русский язык — ключевой критерий, весь контент продукта на русском):

| Tier | Модель | Куда (routing_rules) | Железо (RTX 5080 16GB + 64GB DDR5) |
|---|---|---|---|
| `ollama-fast` | `qwen2.5:7b-instruct` | task_classification | ~4.7GB, целиком в VRAM |
| `ollama-main` | `qwen2.5:14b-instruct` | presentation, email (default) | ~9GB, целиком в VRAM |
| `ollama-deep` | `qwen2.5:32b-instruct` | report, analysis, research | ~20GB, частичный CPU-offload — медленнее, но эти задачи менее интерактивны |

Fallback-цепочки теперь осмысленны (раньше было `fallback: false` — фолбэк на Claude не работал): deep→main, main→fast — деградация к более быстрой/слабой модели лучше, чем полный отказ.

`core/ollama_client.py` теперь передаёт `options.num_ctx` из `model_info.context_window` (fast=8192, main=16384, deep=32768) — без этого длинные промпты тихо обрезались бы до 2048 токенов Ollama-дефолтом.

Модели ещё не скачаны на момент принятия решения (`ollama pull` запущен Виктором, не завершён) — это чисто конфигурационное/кодовое решение, проверено через DI (fake HTTP client), без реального инференса.

## 3. Последствия (Consequences)

### ✅ Плюсы
- Интерактивные задачи (presentation/email) не ждут 32B-модель с CPU-offload.
- Отчёты/аналитика получают более точную модель, раз всё равно менее интерактивны.
- `num_ctx`-баг пойман до того, как стал реальной проблемой при первом реальном прогоне.

### ❌ Минусы / Риски
- Три модели = больше VRAM/диска на диске (~34GB суммарно), больше времени на `ollama pull`.
- Конкретные теги (`qwen2.5:14b-instruct` и т.д.) выбраны по знаниям на январь 2026 — стоит свериться с `ollama.com/library` на актуальность точечных версий (Qwen3 к этому моменту может быть более зрелым вариантом).
- Реальное качество/скорость не проверены (модели ещё качаются) — числа выше ориентировочные, нужна проверка после `ollama pull`.
